# QQ 频道库（gpro）解密原理

> 适用范围：NTQQ Android（本机实测 9.9.27.x，Android 13）
> 定位：本机、本人账号的**只读**数据自查；不注入、不联网、不修改原库。

---

## 一、库在哪里

```
/data/user/0/com.tencent.mobileqq/databases/nt_db/nt_qq_<acct>/gpro_v1-<n>_<uid>.db
                                                  └ 同目录另有 guild_msg.db（频道消息）
```

`<acct>` = `md5( md5(uid) + "nt_kernel" )`；`uid` 可从
`.../files/uid/<QQ号>###<uid>` 这个**明文文件名**直接读到 —— 所以 QQ 号与 uid 都不需要解密、不需要内存。

---

## 二、文件布局

```
[0,1024)      私有头（self-header）
[1024, ...)   页区，每页 4096 字节，共 N 页
```

头结构（与 nt 系库同一套版式，只是 tag 不同）：

| 偏移 | 内容 |
|---|---|
| `[0:16]` | `"SQLite header 3\0"`（伪装魔数，非标准 SQLite） |
| `[16:32]` | 固定参数 `04 00 10 00 ...` |
| `[32:47]` | 库标识，频道库为 `"Guild DB v1.0.0"` |
| `[47:51]` | u32 little-endian = 载荷长度（频道库 = 16） |
| `[51:67]` | 16 字节载荷（本机为可打印 ASCII，如 `Igq5xSewuDZnZrX8`） |
| `[67:1024]` | 全 0 |

**页 1 从偏移 1024 开始**，其前 16 字节即 PBKDF2 的 salt。

---

## 三、口令推导（纯离线）

```
A    = str(QQ号)                              例 "100000001"
P16  = file[51:67]                            头里的 16 字节载荷
K    = md5hex( md5hex(A) + md5hex( sha1_raw(A) ) )
pass = md5hex( md5hex(P16) + K )
```

说明（对应 libgpro.so 里 `orm.cpp` 的密钥推导）：

- `md5hex(x)` = MD5 的**十六进制字符串**（32 字符）
- `sha1_raw(x)` = SHA-1 的**原始 20 字节**，`md5hex(sha1_raw(x))` 即对这 20 字节做 MD5 再取 hex
- 两者都要注意返回形态：**SHA1HashString 返回原始字节，MD5String 返回 hex**

---

## 四、解密参数

| 项 | 值 |
|---|---|
| KDF | PBKDF2-HMAC-**SHA512** |
| 迭代 | **4000** |
| 派生长度 | 32 字节（AES-256） |
| salt | `file[1024:1040]` |
| 页大小 | 4096 |
| **crypto reserve** | **80**（= IV 16 + HMAC-SHA512 64） |

> 注意：头里那句 `PRAGMA cipher_use_hmac = OFF` **实际未生效**（HMAC 仍为 SHA-512）。
> 按 reserve=16 或 48 去解会全部解错。nt 系库（HMAC-SHA1）才是 48。

页布局：

```
页 1 : [salt 16][CT 4000][IV 16][HMAC 64]
页 N : [CT 4016][IV 16][HMAC 64]
```

---

## 五、判据（最容易踩的坑）

SQLCipher 的**页 1 密文里不含 SQLite 魔数** —— 魔数是解密器事后拼回去的
（参见通用做法：解密后写 `b"SQLite format 3\x00" + dec`，再回填页参数）。

所以解密页 1 后，`pt[0]` 对应的是**页内偏移 16 的"页大小"字段**，不是魔数。正确的预言机是：

```python
pt[0:2] == b"\x10\x00"      # 页大小 4096（大端）
and pt[5:8] == b"\x40\x20\x20"   # 64 / 32 / 32（最大/最小嵌入负载、叶子负载比例）
```

用 `pt[:15] in (b"SQLite format 3", ...)` 做判据 = **100% 假阴性**（本文档写作时曾因此白跑 10 万+ 候选）。

## 六、频道数据在哪张表

| 表 | 内容 |
|---|---|
| `t_GPro_Guild_v15` | 频道列表。`guild_info` 是 protobuf，**field 8 = 名称（UTF-8），field 27 = 对外短名** |
| `t_GPro_MemberRoleListInfo_v1_<guildid>` | **每个"我加入/创建"的频道一张表** |
| `t_GPro_Channel_v2` | 子频道（`channel_id` / `channel_name` / `channel_type` / `channel_num`） |
| `t_GPro_CategoryInfo_v1` | 子频道分组（`category_name` / `category_index` / `msg_channel_info_list` 内含该组子频道 id） |
| `t_GPro_Role` | 身份组（`name_` / `display_tag_name_` / `color_` / `count_`；等级组 `type_=100`，名称在 `description_`，形如 `LV.5`） |
| `t_GPro_GuildUserProfile_v3` | 我在各频道的资料（成员名 / 身份组） |
| `t_GPro_Preference` | `self_tiny_id_db_key` = 本人 tiny_id |

### "已加入"的权威判据

```
guildid 出现在 t_GPro_Guild_v15  且  t_GPro_MemberRoleListInfo_v1_<guildid> 表存在
```

只满足后者（有表但不在 Guild_v15）的是**退频道残留**，必须排除。
本机实测：Guild_v15 = 51 行（含"逛过的"），MRL 表 = 45 个，**交集 = 42**，与用户口中的
"加入 41 + 创建 1" 完全吻合。

> 这与早期群验证的"痕迹判据"是同一类错误：**残留痕迹不等于当前事实**，
> 必须回到权威表。群那边用的权威表是 `group_list`，频道这边是 `t_GPro_Guild_v15`。

---

## 七、已知缺口

- **频道成员列表**：`t_GPro_MemberInfo_V2_*` 本地**全为 0 行**（未同步），
  因此"频道成员查询"做不了，只能到"身份组"这一层。
- **频道消息**：`guild_msg.db` 是 nt 系库（另有一套口令），可解；
  但其中一批页只存在于 `-wal`，而 SQLCipher 的 **WAL 帧加密方式与主库页不同**
  （按主库那套解，抽样 8 帧有 7 帧不是合法页头），尚未解出 → 消息可能取不全。
  另：消息表的**子频道**是列 `"40027"`，正文在 `"40800"` 的**内层** field `45101`。

---

## 八、版本风险与自检

该口令推导依赖当前 NTQQ 的实现。腾讯一旦改 KDF 参数或换算法即失效。
因此工具侧必须**先自检再输出**：解密页 1 后过判据，过不了就明确报"当前 QQ 版本不支持"，
**绝不吐出解密不全的数据**。zql 的实现见 `src/decrypt2.go`（`verifyPage1` + `schemeCandidates`）。
